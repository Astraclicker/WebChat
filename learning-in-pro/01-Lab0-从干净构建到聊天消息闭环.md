# Lab 0：从干净构建到聊天消息闭环

## 一、读者、前置知识与完成标准

### 1. 目标读者

这份实验面向第一次接触 CMake、Qt、Boost.Asio 和 MySQL 组合项目的学习者。你不需要预先理解异步 I/O，但应能阅读简单 C++ 函数和终端输出。

### 2. 本实验临时补充的知识

- **进程**：正在运行的程序实例。客户端、服务端和 MySQL 是三个不同进程。
- **端口**：操作系统用来区分网络服务的数字。这里聊天服务监听 9191，MySQL 默认监听 3306。
- **监听**：服务端告诉操作系统“把发往这个端口的新连接交给我”。
- **CMake**：读取 `CMakeLists.txt`，找到编译器和依赖，生成 Ninja 构建规则。
- **Ninja**：按照 CMake 生成的规则真正调用编译器和链接器。
- **JSON 行协议**：每条 JSON 后加 `\n`，接收端以换行符判断一条消息结束。

### 3. 完成标准

不是“执行过命令”，而是你能够：

1. 画出三个进程和两个 TCP 端口；
2. 解释配置、编译、运行为何是不同阶段；
3. 用进程、监听端口、日志、数据库行和协议响应五类证据判断成功；
4. 遇到失败时指出它属于环境、构建、进程、网络、协议还是数据库层。

## 二、先理解为什么需要 Lab 0

陌生仓库最常见的误区，是一开始就阅读大量类和函数。没有运行中的整体，源码中的 `9191`、`async_read_until`、`users` 只是孤立符号。

Lab 0 先建立下面的映射：

```text
源码声明                 运行时证据
server(..., 9191)   ->  ss 显示 9191 正在 LISTEN
async_read_until     ->  一行 JSON 能得到一行响应
switchDatabase       ->  服务端日志显示 MySQL 连接成功
addItem("users")     ->  users 表出现新记录
broadCast            ->  客户端收到 text 类型 JSON
```

## 三、构建、部署、运行不是一回事

### 1. 配置与生成

在 WSL2 的 Ubuntu 终端、仓库根目录执行：

```bash
cmake -S server -B server/build -G Ninja -DCMAKE_BUILD_TYPE=Release
```

参数含义：

- `-S server`：源码入口是 `server/CMakeLists.txt`；
- `-B server/build`：把缓存和 Ninja 规则放到构建目录；
- `-G Ninja`：选择 Ninja 生成器；
- `-DCMAKE_BUILD_TYPE=Release`：请求优化后的发布配置。

成功信号：输出末尾出现 `Build files have been written to`。

失败信号与判断：

- `Could NOT find Boost`：依赖发现阶段失败；
- `未找到 MySQL Connector/C++`：MySQL 开发头文件或库缺失；
- `Cannot find source file`：构建脚本引用了错误源码路径；
- C++ 语法错误尚不会在本阶段出现，因为编译还没开始。

客户端配置同理：

```bash
cmake -S client -B client/build -G Ninja -DCMAKE_BUILD_TYPE=Release
```

### 2. 编译与链接

仍在仓库根目录执行：

```bash
cmake --build server/build --parallel
cmake --build client/build --parallel
```

这一步由 Ninja 调用 `g++`：先把每个 `.cpp` 编译为目标文件，再把目标文件和依赖库链接成可执行文件。

成功信号：

```text
server/bin/Release/server
client/bin/Release/client
```

可以检查动态库是否缺失：

```bash
ldd server/bin/Release/server | grep 'not found'
ldd client/bin/Release/client | grep 'not found'
```

没有输出才是成功信号。`ldd` 的作用是列出程序启动时需要加载的共享库；它不能证明数据库或网络可用。

### 3. 部署

部署指把程序及运行依赖放到目标环境。本项目的 WSL2 本地实验没有独立部署步骤：可执行文件直接使用系统安装的 Qt、Boost 和 MySQL Connector/C++。

Windows 分支会在构建后调用 `windeployqt` 复制 Qt 运行库，这属于部署动作，不是 C++ 编译。

### 4. 运行

运行是操作系统创建进程并执行程序。只有到了这一阶段，端口、数据库账号和协议才会真正参与。

## 四、建立运行架构

### 1. 数据库

MySQL 是独立服务，不会因为聊天室编译成功而自动具备数据库和账号。README 的 SQL 会建立：

- `webchat@127.0.0.1`：服务端用于登录 MySQL 的账号；
- `ChatServer`：项目数据库；
- `ChatServer.users`：保存用户名与密码的表。

检查 MySQL 是否监听：

```bash
ss -ltn | grep ':3306'
```

`ss` 查看内核维护的 socket。出现 `LISTEN` 只证明进程在等连接，不证明用户名或密码正确。

检查项目账号：

```bash
mysqladmin --protocol=tcp \
    -h127.0.0.1 -P3306 \
    -uwebchat -p ping
```

这里交互输入密码，避免把密码留在 shell 历史中。成功信号包含 `mysqld is alive`；`Access denied` 表示网络已到达 MySQL，但身份验证失败。

### 2. 服务端

在第一个 WSL2 终端、仓库根目录执行 README 中的环境变量，然后运行：

```bash
./server/bin/Release/server
```

环境变量是当前进程及其子进程可读取的键值。服务端在 `session.cpp` 中读取 `WEBCHAT_DB_*`，因此必须在启动服务端的同一个终端设置。

成功信号：

```text
Chat server started on port 9191
```

再从另一个终端验证内核状态：

```bash
ss -ltn | grep ':9191'
```

如果日志出现但 `ss` 没有结果，进程可能已经异常退出，应查看日志的最后一条错误。

### 3. 客户端

在第二个 WSL2 终端、同一仓库根目录执行：

```bash
./client/bin/Release/client
```

客户端进程包含两个线程：Qt GUI 线程处理窗口，Asio 网络线程处理 socket。成功连接时终端输出：

```text
[client]connect to 127.0.0.1:9191
```

若图形窗口不出现，检查：

```bash
printf '%s\n' "$DISPLAY"
printf '%s\n' "$WAYLAND_DISPLAY"
```

两者都为空通常表示 WSLg 图形环境不可用。这个问题发生在显示层，与 TCP 是否可连接是两个不同边界。

## 五、沿真实数据流观察一次注册和聊天

### 1. 注册

```text
注册按钮
  -> mainWidget 组装 JSON
  -> chatClient::write 加入发送队列
  -> async_write 写入 TCP
  -> session::doRead 读到换行
  -> createUser 调用 MySQL
  -> 服务端 async_write 返回反馈
  -> chatClient::doRead 收到反馈
  -> Qt 定时器取出消息并显示结果
```

服务端反馈必须是下面两种之一：

```json
{"type":"mysqlCreateUserFeedBack","data":"success"}
```

```json
{"type":"mysqlCreateUserFeedBack","data":"failed"}
```

空字段、重复用户名属于业务失败，必须立即得到 `failed`，不能表现成网络超时。

### 2. 登录

登录成功后，服务端把用户名记录到当前 `session::myUserName`。后续消息转发依赖这个状态；未登录连接没有可用于路由的发送者身份。

### 3. 聊天

当前学习版把接收者固定为 `root`。为了让单客户端也能验证完整链路，服务端同时把消息回显给发送者：

```text
发送者 ──JSON──> 服务端
  ▲                │
  └──── 回显 ──────┘
                   └────> 已登录的 root（若存在）
```

这不是完整聊天产品的最终设计，只是最小可观察闭环。接收者选择、离线回执和消息历史留到后续阶段。

## 六、故障分层表

| 现象 | 所在阶段 | 先检查什么 | 成功信号 |
|---|---|---|---|
| CMake 找不到源文件 | 配置/生成 | `CMakeLists.txt` 路径 | 生成 Ninja 文件 |
| `g++` 报错 | 编译 | 第一条编译错误 | 目标文件生成 |
| `undefined reference` | 链接 | `target_link_libraries` | 可执行文件生成 |
| 服务端立即退出 | 启动 | 最后一条异常日志 | 进程持续存在 |
| 客户端连接失败 | TCP | `ss -ltn | grep 9191` | 9191 为 LISTEN |
| MySQL `Access denied` | 数据库认证 | 账号、来源地址、密码 | `mysqladmin ping` 成功 |
| 注册等待超时 | 协议/业务 | 服务端是否返回一行 JSON | 立即返回 success/failed |
| 发送后无反馈 | 路由/UI | 登录身份、服务端回显 | 收到 text JSON/提示框 |

排错原则：从最靠近失败现象的边界开始收集证据，不要一看到“无响应”就重装所有依赖。

## 七、复盘问题

1. CMake 和 Ninja 分别负责什么？
2. 为什么 `ss` 看到 3306 监听仍可能出现 `Access denied`？
3. TCP 是字节流，服务端怎样知道一条 JSON 在哪里结束？
4. 为什么异步写入时，发送字符串不能在函数返回后立即析构？
5. 为什么单客户端没有回显时，不能直接判断是 WSL 网络问题？
6. Qt 线程和 Asio 线程共享队列时，没有互斥量会违反什么假设？

## 八、可操作练习

### 练习 1：先预测，再验证端口故障

1. 先写下“服务端未启动时客户端会打印什么”；
2. 停止服务端，只启动客户端；
3. 用 `ss` 和客户端日志验证；
4. 解释预测与实际差异。

### 练习 2：区分业务失败与网络超时

1. 预测重复注册的响应；
2. 注册同一用户名两次；
3. 观察服务端日志和客户端提示；
4. 解释为什么第二次失败不应等待 5 秒。

### 练习 3：观察数据库状态

注册一个临时用户后执行：

```bash
mysql --protocol=tcp -h127.0.0.1 -P3306 -uwebchat -p \
    -e 'SELECT userName FROM ChatServer.users;'
```

先预测结果，再运行并解释 GUI 成功提示与数据库行之间的因果关系。
