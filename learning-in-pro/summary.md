# WebChat 学习总览

## 目标读者

本文档面向只掌握少量 C++ 语法、尚不熟悉 Linux 构建、TCP、事件循环和数据库连接的学习者。

已经假定你知道：变量、函数、类、条件分支，以及“客户端向服务端发送数据”的直观概念。

需要在项目中临时补充：

- CMake 的配置、生成、编译三个阶段；
- 进程、端口和 TCP 连接的关系；
- Qt 与 Boost.Asio 为什么各自需要事件循环；
- JSON 行协议如何划分消息边界；
- MySQL 账号、数据库和表分别解决什么问题；
- 异步操作期间对象与缓冲区的生命周期。

完成当前阶段后，你应该能回答：

1. 客户端点击登录后，数据依次经过哪些函数和进程？
2. 为什么“二进制文件生成成功”不能证明聊天室已经跑通？
3. 为什么 TCP 消息末尾需要换行符？
4. 为什么 Asio 线程和 Qt 线程不能无锁读写同一个 `std::deque`？
5. 如何区分构建失败、数据库失败、端口失败和协议失败？

## 当前运行架构

```text
Qt 客户端进程
├─ GUI 线程：Qt 事件循环、按钮、提示框
└─ 网络线程：Boost.Asio 事件循环
          │
          │ TCP 127.0.0.1:9191
          ▼
服务端进程
├─ Boost.Asio：接收连接、按换行读取 JSON、转发消息
└─ MySQL Connector/C++
          │
          │ TCP 127.0.0.1:3306（README 默认值）
          ▼
MySQL 进程 / ChatServer.users 表
```

## 已掌握与已验证

- 客户端、服务端能在 Ubuntu 24.04 / WSL2 使用 CMake 3.28 干净构建；
- 服务端能连接 MySQL，并完成新用户注册、重复注册失败、登录；
- 单客户端发送消息能得到服务端回显；
- 两个已登录客户端可按用户名转发消息；
- 空注册请求会立即返回失败，而不是等待客户端超时；
- 客户端入口文件路径、端口不一致、异步发送缓冲区生命周期等问题已有源码注释。

## 暂时作为黑盒的部分

- Qt 控件的绘制实现；
- Boost.Asio 内部如何调用 `epoll`；
- MySQL Connector/C++ 的网络协议；
- SQL++ 中与当前服务端无关的通用 CRUD 能力。

“黑盒”不等于永远不学，而是第一遍先建立完整可运行链路，再逐层打开。

## 已知设计边界

- 客户端仍把聊天接收者固定为 `root`；
- 界面只用短暂提示框展示消息，没有历史记录；
- 接收者离线时没有投递失败回执；
- 每个 TCP 会话同步创建一条 MySQL 连接，并发量增大时会阻塞事件循环；
- 密码以明文保存，只能用于本地学习；
- 协议没有消息大小上限、版本协商和完善的错误码。

这些边界不是本轮“跑通”必须扩展的功能。后续学习时应一次只选择一个问题，先写可验证目标，再修改架构。
